# 人-Agent 协作的软件工程方法论讨论记录

> 日期：2026-04-12
> 背景：以 ext-saladict 的 MV2 -> MV3 迁移为试验场，讨论如何把原本由多人协作完成的软件工程执行流程，重构为“人负责目标与决策，Agent 并发负责分析、展开、补全、验证”的协作模式

---

## 1. 这份记录讨论的主问题

当前项目表面上是在做浏览器扩展的 MV3 迁移，但更核心的主线任务其实不是“把迁移做完”，而是：

- 探索如何与 AI / Agent 协作完成陌生领域任务
- 识别这种协作模式中的系统性痛点
- 研究怎样把原本由多人协作完成的软件工程流程，转化为“人 + Agent”协作，并显著提升效率

换句话说：

- MV3 迁移是试验场，不是唯一目标
- 真正的研究对象是协作结构，而不是某个具体技术栈

---

## 2. 这件事不是脱离传统软件工程的新问题

当前讨论并不是在发明一套与传统软件工程完全割裂的新流程。

传统软件工程本来就有一条比较清晰的执行链路：

- `Epic`
- `Feature`
- `User Story`
- `BDD Scenario / 测试案例`
- `Tech Story`
- Implementation

在常规项目里，通常是：

- PM 主导 `Epic / Feature / User Story`
- 团队通过 `BDD Scenario / 测试案例` 冻结产品基线
- 开发侧再往下拆 `Tech Story`

因此，这次讨论的核心不是“换掉传统流程”，而是：

> 如何把原本由多人协作完成的这条链路，改造为人-Agent协作完成，并利用 Agent 的可并发性与低输入成本提升吞吐量。

---

## 3. 当前团队已有的实际开发模式

当前团队的执行模式并不是“只有 user story”，而更接近：

- `User Story`
  - 表达“我想要什么”
- `BDD Scenario / 测试案例`
  - 表达“什么算做到了”

这意味着团队已经具备一套相当成熟的产品基线与验收基线机制。

因此问题不在于缺少 `User Story + BDD` 的方法，而在于：

- 在迁移类任务中，PM 无法也不愿意手工完整梳理所有 story / scenario
- 很多规格实际藏在旧系统、旧代码、旧行为中
- 所以需要 AI 参与到“基线补全”过程中

---

## 4. 迁移任务的特殊性

迁移任务和常规新功能开发不同。

常规新功能开发：

- 产品规格主要来自 PM
- 需求从上往下定义

迁移任务：

- 高层目标仍来自 PM，例如“完成 MV3 迁移”
- 但大量具体规格不在 PM 脑中，而是在旧系统里
- PM 可能只了解主流程，不了解全部边角行为
- PM 也不愿意做大规模细节确认

所以迁移任务的关键变化是：

> `Feature / User Story / BDD Scenario` 不再完全由 PM 显式提供，而需要 AI 从旧系统中发现、提炼和补全。

这类任务更像是：

- 正常项目：正向写规格
- 迁移项目：逆向提规格

---

## 5. 人性前提：人只想做决策，不想做细节劳动

这次讨论里一个非常关键的前提是：

- 人都是懒的
- 大家更愿意做决策，而不是做细节确认

因此，一个现实可行的人-Agent协作流程不能假设：

- PM 会逐条确认几十个 feature
- PM 会逐条补完所有 user story
- PM 会逐条审查所有 BDD scenario

如果流程要求人做这些高成本细节劳动，这个流程就不会长期跑得动。

因此，协作系统必须满足：

- 人负责拍板、定方向、定优先级、定风险接受度
- Agent 负责大部分细节展开、补全、检查和验证

---

## 6. 这次讨论的一个关键修正

一个过于理想化但不现实的说法是：

- PM 只给 North Star Intent
- AI 负责把它扩展成 Executable Intent
- AI 只在“必须决策”的地方打断 PM

这套说法的问题在于：

- “必须决策”不能由 AI 主观定义
- 否则 AI 会按自己的理解决定何时升级
- 人与 AI 的理解未必一致

这就引出了传统软件工程里非常重要的概念：

## 6.1 基线（Baseline）

传统软件工程里，真正约束后续实现与变更的，不是“开发者觉得这件事大不大”，而是：

- 当前产品基线是什么
- 当前技术基线是什么

对这次讨论来说，可以把基线分成两层：

### 产品基线

由以下部分组成：

- `Epic`
- `Feature`
- `User Story`
- `BDD Scenario / 测试案例`

它回答的是：

> 产品应该长什么样

### 技术基线

由以下部分组成：

- `Tech Story`
- 技术实现约束
- 承接关系
- 验证手段

它回答的是：

> 技术实现应该长什么样，能否承接产品基线

因此，“是否需要升级给人决策”不该由 AI 主观判断，而应该由下面的事实决定：

- 当前工作是否触碰了已冻结的产品基线
- 当前技术基线是否无法承接产品基线

也就是说：

> 决策升级条件应该由“是否触碰基线”来定义，而不是由 AI 自己判断“这件事够不够重要”。

---

## 7. 所以问题的本质不是“AI 什么时候问人”

真正关键的问题是：

> 如何建立并冻结基线

因为在基线还没有明确之前：

- 什么算偏离，不清楚
- 什么算回归，不清楚
- 什么需要升级，不清楚

在迁移类任务中，这一点尤为突出，因为旧系统的很多规格没有显式写出来。

因此，对这类任务更准确的描述是：

- PM 负责给出高层 `Epic`
- AI 负责从旧系统中提炼候选产品基线
- 人对“基线版本”做冻结和修正
- 然后 AI 再围绕该基线做技术承接和实现验证

---

## 8. 这不是新发明，而是传统流程在 AI 时代的结构重构

传统模式的问题不在逻辑，而在吞吐量：

- 人很难并发
- 人的输入成本高
- 会议成本高
- 上下文切换成本高
- 大量细化工作机械、重复、低效

Agent 的真正优势不只是“会写代码”，而是：

- 可以并发
- 可以低成本尝试
- 可以快速产出候选方案
- 可以承接大量高成本细节劳动

因此，这次讨论得出的核心命题不是：

- 让 AI 替代 PM

而是：

> 如何把原本由多人协作完成的规格拆解、基线补全、技术承接与验证过程，重构为人负责目标与决策、多个 Agent 并发负责分析、展开、补全与验证的协作系统。

---

## 9. 人-Agent 协作中的职责重分配

### 人的职责

人的价值主要在：

- 定目标
- 定范围
- 定优先级
- 定风险接受度
- 冻结和修正基线
- 对冲突选项拍板

人的职责不是：

- 手工穷举所有 story
- 手工梳理所有测试案例
- 手工追踪全部实现细节

### Agent 的职责

Agent 的价值主要在：

- 从旧系统中发现和提炼 feature / story / scenario
- 补全缺失的 BDD 场景
- 做 tech story 拆解
- 做 probe / test / validation 设计
- 并发执行实现、检查、一致性校验、证据收集

因此：

- 人负责高价值决策
- Agent 负责高成本细节劳动

## 11. 交接物（Artifact）比 Prompt 更重要

人-Agent协作如果长期依赖 prompt 和对话，会很快失控。

原因是 prompt / 对话：

- 不易冻结
- 不易 diff
- 不易并发复用
- 不易追溯
- 不适合交接

因此，真正应该标准化的不是 prompt，而是 artifact。

目前讨论里已经形成一个重要判断：

> 在执行阶段，协作必须从“对话驱动”切到“artifact 驱动”。

已讨论到的关键 artifact 类型包括：

- `Intent Package`
  - 记录高层目标、范围、优先级、非目标
- `Baseline Package`
  - 记录当前冻结的产品基线
- `Work / Tech Story Package`
  - 记录技术承接与实现拆解
- `Evidence Package`
  - 记录当前实现对基线的验证证据
- `Decision Package`
  - 记录需要人拍板的问题、选项与代价

其中最核心的交接物很可能是：

- `Baseline Package`

因为它同时连接：

- PM 的目标
- Feature / User Story
- BDD Scenario
- 技术承接范围
- 后续验证标准

这部分已形成高共识，但模板和执行规则仍待继续细化。

---

## 12. BDD / SDD 在这个问题里的位置

这轮讨论的一个重要结论是：

- `BDD` 更适合冻结和表达产品行为基线
- `SDD` 更适合在基线冻结后驱动技术实现与验证

但两者都不能单独解决迁移任务的核心问题，因为迁移任务还缺一个前置阶段：

- 旧系统行为发现
- 也即基线补全 / baseline discovery

因此，一个更完整的执行框架更像是：

1. 从旧系统发现和提炼基线
2. 用 `BDD Scenario` 冻结关键行为基线
3. 用 `SDD / Tech Story` 驱动实现与承接

## 13. 当前已经形成的高价值共识

截至这轮讨论，已经形成的核心共识可以压缩为下面几条：

### 13.1

这次项目真正要研究的，不只是 MV3 迁移，而是：

> 如何把传统多人协作的软件工程执行流程，改造成更高效的人-Agent协作流程。

### 13.2

这套方法论并不脱离传统软件工程，而是仍然落在：

- `Epic`
- `Feature`
- `User Story`
- `BDD Scenario`
- `Tech Story`

这条经典链路上。

### 13.3

迁移任务的特殊性在于：

- PM 不能也不愿意穷举所有 story / scenario
- 规格大量藏在旧系统里
- 因此需要 AI 主导“基线补全”

### 13.4

“是否该升级给人决策”不能由 AI 主观定义，而应该由“是否触碰已冻结基线”来定义。

### 13.5

人-Agent协作里最该标准化的，不是 prompt，而是 artifact。

### 13.6

整个协作系统必须符合一个现实前提：

- 人只想做决策
- 不想做高成本细节确认

所以流程设计的方向应该是：

> 尽可能把细节展开、补全、检查、验证交给 Agent，把人保留在少量高价值决策点上。

---

## 14. 待继续讨论的问题

当前讨论还没有完全收敛，后续值得继续展开的问题包括：

- `Baseline Package` 的最小模板应该长什么样
- 哪些内容属于产品基线，哪些属于技术基线
- AI 从旧系统补全 `User Story / BDD Scenario` 时，输入源与输出格式应如何标准化
- 多个 Agent 并发工作时，如何共享冻结基线并避免各自脑补
- `Decision Package` 何时产生、如何压缩成人可快速拍板的形式
- `Evidence Package` 如何和基线版本、实现版本建立稳定绑定

---

## 15. 一句话总结

这轮讨论的核心收敛点可以表述为：

> 当前要研究的不是“AI 是否能写代码”，而是如何让 AI / Agent 参与并重构传统的软件工程执行链路，使原本依赖多人串行完成的规格拆解、基线补全、技术承接和验证过程，变成“人负责目标与决策，Agent 并发负责分析、展开、补全与验证”的协作系统。
