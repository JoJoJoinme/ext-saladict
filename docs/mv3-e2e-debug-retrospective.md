# Saladict MV3 端到端迁移排障复盘

> 日期：2026-04-10
> 面向对象：不懂前端、但想学会怎么排查浏览器扩展问题的人
> 配套文档：[`../MV3_MIGRATION.md`](../MV3_MIGRATION.md)

---

## 1. 先说结论

这次任务真正困难的地方，不是“把 MV2 代码机械地改成 MV3 语法”，而是“证明这个扩展在真实 Chrome 里真的能用”。

很多 AI 或开发者都会在下面这些时刻过早宣布成功：

- `npm run build` 通过了
- 单元测试通过了
- 扩展能被 Chrome 加载了
- 面板 UI 弹出来了

但这些都不等于真正完成。

这次我最终采用的成功标准是：

1. Chrome 能加载构建后的 MV3 扩展。
2. 打开真实网页后，content script 确实被注入。
3. 用户划词后，查词浮标能出现。
4. 点击浮标后，查词面板能出现。
5. 面板里能显示真实词典结果，而不是空白壳子。
6. 浏览器保持打开，让人可以亲手再试一遍。

也就是说，我不是把“构建成功”当成终点，而是把“真实用户操作链路走通”当成终点。

---

## 2. 我是怎么想这个问题的

### 2.1 先把整条链路画出来

浏览器扩展的查词功能，表面上看只是“划个词，弹个面板”。但实际运行链路通常是这样的：

```text
网页里的文字选择
  -> content script 监听到 selection
  -> 扩展注入自己的 UI 容器
  -> 发送消息给 background/service worker
  -> background 再去做权限、状态、字典请求、辅助页面等操作
  -> 结果通过消息回到 content 侧 Redux / React
  -> React 把词典结果渲染出来
```

只要这条链路里任何一个箭头断了，用户看到的现象都可能是同一句话：

> “面板没反应。”

所以第一步不能急着改代码，而是要先问：

> “到底是哪一个箭头断了？”

这个思路非常重要。因为“面板没反应”只是最终症状，不是根因。

### 2.2 我采用的排查原则

我整个过程基本一直在重复一个固定循环：

1. 先记录现象。
2. 对现象提出一个最可能的猜测。
3. 想办法用最小证据去验证这个猜测。
4. 猜测成立才修代码。
5. 修完回到真实链路重新验证。

换句话说，不是“觉得这里像 bug 就改”，而是：

> 现象 -> 猜测 -> 证据 -> 修复 -> 回归

这也是我最想让你学到的东西。

## 3. 一开始先做了什么

### 3.1 先对“成功”下定义

你一开始就反复强调一件事：

- 不是只看 e2e testcase
- 不是只看 build
- 要拉起真实浏览器
- 要加载扩展
- 要真实划词
- 最后还要保留浏览器让你自己试

这个要求非常关键。它相当于帮我把“验收标准”钉死了。

如果没有这个标准，任务很容易在“测试都过了，看起来差不多了”时提前结束。

### 3.2 先扫描仓库，确认当前工程状态

我先做的不是乱改代码，而是先理解这个 repo 的基础状态：

- 现在已经迁移到 WXT + Vite，不再是老的 MV2 Webpack 体系。
- 仓库里已经有一份迁移工程记录，也就是说并不是从零开始。
- 扩展目标是 Chrome/Edge 的 MV3，不再追 Firefox/Safari。
- 代码里同时存在 background、content、selection、popup、offscreen 等多条运行链路。

这一步的目的是建立“地图”。如果不知道地图，后面看到任何报错都很容易瞎猜。

### 3.3 先准备真实验证工具，而不是只看代码

因为目标是“端到端真的 work”，所以我很快就把注意力放在运行验证工具上，而不是只做静态阅读。

后面我主要依赖了几类验证手段：

- 真实 Chrome 加载打包后的扩展
- Playwright 驱动真实扩展
- 手动打开浏览器并保留窗口
- 运行时探针脚本，验证消息和返回值
- DOM/console/pageerror 采集脚本
- Chrome DevTools MCP 辅助确认扩展是否真的被加载

这里的核心思想是：

> 代码阅读只能给“猜测”，运行证据才能给“结论”。

## 4. 第一类问题：先证明扩展到底有没有被真正加载

### 4.1 现象

当时我尝试通过浏览器调试链路去验证扩展时，发现一个很怪的现象：

- 命令行明明传了 `--load-extension=...`
- 但在某些受控浏览器会话里，`chrome://extensions` 里看到的扩展数量是 `0`

这时候有两个完全不同的可能性：

1. 扩展包本身坏了，Chrome 根本加载不了。
2. 扩展包其实没坏，是我当前用来调试的那条浏览器/MCP 链路没有真的把扩展挂进去。

这两个结论差别很大。

如果是第 1 种，应该修产品代码。
如果是第 2 种，应该修调试环境或换验证方式。

### 4.2 我的猜测

我当时的猜测不是立刻认定“扩展坏了”，而是把问题拆成：

- `dist/chrome-mv3` 产物是否有效？
- MCP 控制的 Chrome 会话是否真的支持扩展类别？
- 当前调试协议是否把“浏览器能启动”和“扩展真加载”混为一谈了？

### 4.3 我怎么验证

我做的验证不是一个，而是一组：

- 检查构建产物目录和 manifest 是否存在。
- 在浏览器里看 `chrome://extensions` 的真实状态。
- 检查 MCP 配置，确认是否开启扩展相关 category。
- 用扩展相关的 MCP 能力去 `install_extension`、`reload_extension`、`list_extensions`。

后面确认到一个独立事实：

- 只靠最初那条 MCP 受控 Chrome 会话，并不能稳定代表“扩展已真实加载可调试”。
- 在补上 `--category-extensions=true` 后，MCP 至少能明确看到扩展安装和 reload 状态。
- 但它在某些页面和动作上仍有限制，比如不能直接把它当成完整的人类浏览器替代。

### 4.4 这一步的结论

这里我得到的关键结论不是“已经修好”，而是：

> 扩展包并不等于没法加载，问题里混着一部分调试环境限制。

这个结论非常重要，因为它避免我在错误方向上浪费很多时间。

如果我这时误判成“dist 包坏了”，后面就可能开始大规模重写 manifest、入口文件、构建配置，最后白忙。

### 4.5 这一阶段学到的排查方法

当你看到“工具里没有出现扩展”时，第一反应不要是“产品坏了”，而应该问：

1. 是产品坏了？
2. 是调试工具没挂上？
3. 是这个工具的能力边界不够？

先把这三件事分开，排查会快很多。

## 5. 第二类问题：扩展加载后，页面里到底有没有注入成功

### 5.1 现象

一个典型误区是：只要 Chrome 里看到了扩展，就觉得“已经差不多好了”。

其实不是。

因为浏览器扩展能“装上”，不代表 content script 已经在网页里正确运行。

所以我接下来关心的是另一个更具体的问题：

> 页面里到底有没有出现 Saladict 自己注入的根节点？

比如这种 UI 根容器：

- `saladict-saladbowl-root`
- `saladict-dictpanel-root`

如果这些节点没有出现，说明问题还停留在“注入层”。

### 5.2 我的猜测

这里的可疑点主要有几类：

- WXT 入口文件没有被正确声明。
- 原来 MV2 的 selection 逻辑迁移后没有真正挂到 MV3 content script 上。
- manifest 看起来对，但实际匹配页面或注入时机不对。

### 5.3 我怎么验证

验证方式非常朴素：

- 去看 WXT 入口文件。
- 去看 selection content script 的入口映射。
- 在实际页面里直接检查这些根节点是否存在。

这一步不是靠“想象内容应该被注入”，而是直接问 DOM：

> “你到底有没有这个节点？”

### 5.4 对应修复

这里最终落到的修复点之一，是把 selection 这条内容脚本入口作为明确的 WXT entrypoint 处理，也就是后来的：

- `src/entrypoints/selection.content.ts`

这类问题的本质，是迁移时“代码文件存在”不等于“构建系统会把它当成真正入口”。

这个坑在 MV2 -> MV3、Webpack -> WXT 迁移里很常见。

### 5.5 这一步的教训

浏览器扩展里，“文件在仓库里”和“文件在浏览器里真的跑起来”是两回事。

遇到注入问题时，要优先看：

- 入口有没有被构建系统识别
- manifest 最终产物长什么样
- 目标页面里有没有实际 DOM 证据

## 6. 第三类问题：为什么请求会超时，而不是报明确错误

### 6.1 现象

当注入和基本 UI 逐渐有了之后，问题开始进入更隐蔽的阶段。

我通过运行时探针看到了很关键的现象：

- `QUERY_QS_PANEL timed out after 5000ms`
- `FETCH_DICT_RESULT timed out after 70000ms`

这类现象说明一件事：

> 不是“拿到了错误返回”，而是“消息链路中途有人不回了”。

这种问题往往比普通异常更难排查，因为它看起来像“没反应”。

### 6.2 我的猜测

这里我的核心猜测是：

> 迁移到 MV3 后，某些消息辅助逻辑还在偷偷假设自己运行在 `window` 上下文里。

为什么会这样猜？

因为 MV2 时代很多 background page 是带 DOM / `window` 的，而 MV3 的 background 变成了 service worker。service worker 没有页面级的 `window` 环境，这类假设很容易失效。

尤其是下面这种代码味道，通常非常危险：

- 依赖 `window.pageId`
- 假设当前运行环境一定有 `window`
- 自发消息时默认认为自己在页面里

### 6.3 我怎么验证

我没有直接大改 background，而是先做了两件事：

1. 写运行时探针，去测试消息到底是在发送、接收，还是回包阶段断掉。
2. 读消息相关辅助层代码，重点看那些“看起来很方便”的封装函数。

后来定位到一个很关键的地方：

- `src/_helpers/browser-api.ts`

这里的自发消息和监听逻辑，在 MV3 service worker 场景下还保留了旧时代的运行环境假设。

### 6.4 对应修复

修复思路不是“把所有逻辑重写”，而是：

- 先判断当前是否真的在有 `window` 的环境里。
- 把“当前 pageId”获取逻辑改成在不同上下文下都安全。
- 避免 service worker 走到依赖页面上下文的自消息路径。

最后落地成了类似下面这类能力：

- `hasWindowContext()`
- `getCurrentPageId()`

并相应修复：

- `messageSendSelf()`
- `messageAddListener()`

### 6.5 修复后的结果

修复后，探针现象发生了本质变化：

- 之前是超时
- 之后至少能拿到正常返回或明确的 false / 数据结果

这说明链路终于不再“黑洞化”。

这一步特别值得学，因为它体现了一个排查原则：

> 比起“有没有成功”，先看“有没有响应”。

从“完全超时”变成“返回 false”，虽然功能还没全通，但已经说明你修对了一个层级。

## 7. 第四类问题：后台辅助页面创建失败

### 7.1 现象

在继续追后台能力时，我又通过探针拿到了一个非常具体的错误：

> `Invalid value for state`

这类报错的价值很高，因为它终于不是模糊的“没反应”，而是一个明确的 API 参数错误。

### 7.2 我的猜测

我当时的猜测是：

> 某个创建辅助页面/窗口的逻辑，沿用了旧代码里的窗口状态参数，但这个参数在当前 MV3 路径下不合法。

### 7.3 我怎么验证

我回去读了相关辅助逻辑，最后定位到：

- `src/background/offscreen-helper.ts`

里面存在创建窗口时传 `state: 'minimized'` 的路径。

### 7.4 对应修复

我把这个非法状态参数去掉，让创建逻辑回到浏览器能接受的最小可用参数集合。

### 7.5 结果

修复之后，相关辅助页面可以被正常创建，后台能力链路少了一个隐藏中断点。

这里的教训是：

> 当浏览器 API 明确告诉你“参数不合法”时，优先相信浏览器，不要先怀疑业务逻辑。

先把 API 调用变成合法调用，再看业务是否继续有问题。

## 8. 第五类问题：为什么面板已经弹出来了，但用户还是觉得“没有响应”

### 8.1 这是一个关键转折点

你后来给了一个非常重要的真实反馈：

> “我看到了查词面板，但是似乎查词结果一直没有响应”

这句话表面像抱怨，实际上对排查非常有价值。

因为它说明：

- 扩展已经加载了
- 页面注入已经发生了
- 划词监听已经工作了
- 面板外壳至少能渲染出来

于是问题范围立刻缩小到更后面的层级：

- 数据没回来？
- 数据回来了但渲染炸了？
- 实际选中的文本不对？
- 有返回但 UI 没把“无结果”表现出来？

这就是为什么真实用户反馈很重要。它能帮你把排查范围一下砍掉一大半。

### 8.2 我的第一层猜测：渲染可能炸了

因为“壳子有了，内容没有”很像前端渲染层报错。

如果 background 完全没工作，通常连后续状态都不一定能推进到这个程度。

所以我开始收集更细的前端证据：

- console 错误
- pageerror
- 请求失败
- 面板内部 DOM 结构

### 8.3 我怎么验证

为了避免靠肉眼盯浏览器，我补强了一个诊断脚本：

- `dev/selection-dump.mjs`

这个脚本会尽量把“你看到的空白面板”拆成可分析的数据：

- 实际选中的文本是什么
- 页面有没有报错
- 面板 DOM 里有哪些节点
- 某些字典项内部到底渲染了什么

最后我抓到一个非常有用的错误：

> `TypeError: (a.default || a).toString is not a function`

而且它指向了渲染层相关文件：

- `src/content/components/DictItem/DictItemBody.tsx`

### 8.4 对应修复

这个问题本质上是动态样式导入在新构建体系下的模块形态变化了。

简单说就是：

- 旧写法默认拿到的是可直接处理的样式字符串
- 新构建链路下，导入结果变成了模块对象命名空间
- 继续粗暴 `.toString()` 就会炸

所以修复方式是：

- 改成 `?inline` 形式导入样式
- 安全地读取 `styleModule.default`
- 不再对整个模块对象直接 `.toString()`

### 8.5 结果

这一步修完后，前端渲染层的硬崩溃消失了。

注意，这里我仍然没有宣布“全部好了”。

因为“一个崩溃消失”只说明修掉了一个问题，不代表后面没有别的问题。

## 9. 第六类问题：原来测试输入本身就是错的

### 9.1 现象

修完渲染错误后，事情变得更微妙了：

- 面板能打开
- 报错少了
- 但视觉上依然可能像“没结果”

这时候最危险的事情，就是继续在复杂代码里盲改。

我当时停下来问了一个最基本的问题：

> “我们真的选中了自己以为选中的那个词吗？”

### 9.2 我的猜测

我怀疑问题不一定在“字典请求挂了”，而可能在“测试动作选错了文本”。

因为自动化拖选文本时，如果起止坐标不准，很容易选到：

- 少一个首字母
- 多带一个相邻单词
- 带上换行或额外空格

对于词典查询来说，这种误差足以把结果完全变掉。

### 9.3 我怎么验证

这一步我没有凭感觉，而是直接把“真实 selection 字符串”打出来看。

结果非常关键：

- 我以为选中的是 `"Example"`
- 实际选中的是 `"xample Domain"`

这一下很多现象就解释通了。

因为对词典接口来说：

- `example` 是标准词条
- `xample Domain` 基本不是正常单词查询

### 9.4 我继续验证：到底是接口坏了，还是输入坏了

为了避免再次误判，我又做了一层对照验证：

- 用探针直接请求字典 `example`
- 再请求 `xample Domain`
- 对比返回数据

结果是：

- 对 `example`，Bing 能返回正常词条和例句
- 对 `xample Domain`，有的词典返回 `null`
- 有的返回结构存在，但内部段落是空字符串

于是结论非常明确：

> 不是扩展整体不会查词，而是我们测试时选错了文本，导致拿到了“正常但无意义”的无结果返回。

### 9.5 对应修复

这一步的修复不是业务逻辑，而是测试动作本身。

我在两个验证脚本里都加了更精确的文本定位逻辑：

- `test/e2e/manual-open-browser.mjs`
- `test/e2e/playwright-e2e.mjs`

核心思路是：

- 不再用粗糙的拖拽大概框住整个标题
- 而是先计算具体目标单词 `"Example"` 的真实文本矩形
- 再只拖拽这个单词的范围

对应的辅助函数就是：

- `getTextRect(page, selector, targetText)`

### 9.6 结果

修完后，真实选中的文本终于变成：

- `"Example"`

然后查词结果就真的出来了，Bing 的标题和例句都能看到。

这一段是整个任务里最值得记住的一个排查 lesson：

> 当系统输入错了时，下游所有模块都可能看起来像坏了。

所以遇到“结果不对”时，一定要先确认输入到底是不是你以为的那个输入。

## 10. 第七类问题：产品其实 work 了，但 UX 仍然会让人以为它坏了

### 10.1 现象

就算上一步已经证明了“选准 `Example` 会有正常结果”，我还是注意到一个现实问题：

如果用户真的选中了一个查不到的内容，当前 UI 表现仍然很差。

它会出现一种很迷惑的状态：

- 面板开了
- 某些 dict item 有一点高度
- 但里面几乎是空白

对于用户来说，这和“卡住了”“没响应”几乎没区别。

### 10.2 我的猜测

这里我判断：

> 这不再是底层运行 bug，而是一个验收层面的产品问题。

也就是说，逻辑未必错，但用户感知是错的。

如果不修这一层，就算代码 technically work，真实体验仍然会被判定为失败。

### 10.3 我怎么验证

我继续用 `dev/selection-dump.mjs` 去看无结果场景下各个字典项内部到底有什么。

我看到的是：

- 有些返回结构存在
- 但 `paragraphs` 是空字符串
- DOM 里没有真正可读的内容

这说明前端把“查无结果”误当成“有东西可渲染”，最后渲染出了一些几乎看不见的空块。

### 10.4 对应修复

我在下面这些文件里补了显式空状态：

- `src/content/components/DictItem/DictItemBody.tsx`
- `src/content/components/DictItem/DictItem.scss`
- `src/_locales/zh-CN/content.ts`
- `src/_locales/zh-TW/content.ts`
- `src/_locales/en/content.ts`

核心逻辑是：

- 判断这个结果是否真的“有可渲染内容”
- 如果请求已经结束但没有可读结果，就显示：
  - `未找到结果`
  - `No result`

### 10.5 结果

这样一来，即使用户选中了奇怪文本，也不会再看到“像挂了一样的空白面板”，而是能明确知道：

> 这次没有查到结果。

这一步很像产品上的“错误提示设计”，它不是最底层的 bug fix，但对真实可用性非常重要。

## 11. Chrome DevTools MCP 在这次排查里到底起了什么作用

你多次强调最好结合 MCP，这个建议是有帮助的，但它的帮助方式和“直接替你完成所有调试”不完全一样。

### 11.1 MCP 真正帮到我的地方

MCP 主要帮我确认了这些事实：

- 扩展有没有被 install
- 扩展能不能 reload
- 扩展 ID 是什么
- 某个受控浏览器会话里，扩展 category 有没有真的启用
- 在某些页面里，是否看得到注入后的根节点

换句话说，MCP 很适合回答：

> “浏览器当前状态到底是什么？”

### 11.2 MCP 没法直接替代的部分

在这次环境里，MCP 受控 Chrome 也有一些边界：

- 某些扩展页面直接打开会受限
- 某些协议动作不存在
- 某些会话里即使命令行带了扩展参数，也未必等价于人工打开的真实桌面浏览器

所以我最后采取的是：

- 用 MCP 辅助定位“扩展加载状态”和“环境事实”
- 用真实 Chrome + 自动化脚本完成最终端到端验收

这不是“谁对谁错”，而是工具分工问题。

### 11.3 这里的经验

调试工具最容易让人犯的错误是：

> 把工具观察到的世界，误当成产品真实世界的全部。

工具永远有边界。

真正稳妥的做法是：

- 用工具缩小问题范围
- 用真实运行场景做最终确认

## 13. 粗略时间线

下面不是精确工时统计，只是帮助理解整个任务是怎么推进的。

### 阶段 1：先建立验收标准和验证路径

大意是：

- 先理解 repo 现状
- 先接受“必须真实加载扩展并真实划词”这个标准
- 先搭出真实浏览器验证链路

这一阶段的价值，不在于修 bug，而在于避免后面走偏。

### 阶段 2：排除“调试工具本身”的干扰

大意是：

- 确认扩展到底有没有真的被加载
- 分离“产品 bug”和“调试会话限制”
- 让 MCP 至少能提供可信的加载状态事实

这一阶段如果做不好，后面所有结论都可能立在沙子上。

### 阶段 3：修通后台消息与辅助能力

大意是：

- 通过探针抓到 timeout
- 修 service worker 下的消息辅助逻辑
- 修辅助页面创建参数错误

这一步是在修“链路会不会断”的问题。

### 阶段 4：修通前端渲染

大意是：

- 面板壳子能出现，但内容层报错
- 抓 pageerror
- 修样式动态导入在新构建体系下的运行时兼容问题

这一步是在修“数据到了以后能不能显示”的问题。

### 阶段 5：修正测试动作与最后的 UX 误导

大意是：

- 发现选中的根本不是预期单词
- 改精确选词逻辑
- 发现无结果时 UI 过于像“卡住”
- 增加 empty state

这一步是在修“人为什么会误判它没 work”的问题。

### 阶段 6：最终验收

最终采用的是一组叠加证据，而不是单一证据：

- 构建通过
- Playwright 真扩展 e2e 通过
- 手动浏览器脚本能打开真实浏览器并完成划词查词
- 浏览器保持打开，允许人再次手试

只有这些证据叠在一起，我才认为迁移真正收口了。

## 15. 如果你以后自己排查类似问题，可以照着这个顺序来

下面这套顺序，几乎可以复用到所有浏览器扩展或前端交互问题里。

### 第 1 步：先定义什么叫“真的成功”

不要说“差不多能用”。

要改成这种可检查句子：

- 扩展能加载
- 内容脚本注入成功
- 目标交互能触发
- 后台有响应
- 页面能渲染真实结果
- 人亲手再试一次也通过

### 第 2 步：把运行链路画出来

哪怕只是一张很粗糙的链路图，也比脑子里一团糊强得多。

一旦你能画出：

```text
输入 -> 监听 -> 消息 -> 后台 -> 请求 -> 回包 -> 渲染
```

你就知道下一步该查哪一段。

### 第 3 步：每次只证明一个环节

比如先证明：

- 扩展已加载

再证明：

- 内容脚本已注入

再证明：

- 消息不是超时而是有返回

再证明：

- 返回的数据不是空

不要一口气同时怀疑十件事。

### 第 4 步：优先把“模糊现象”变成“明确证据”

例如把：

- “好像没反应”

变成：

- 具体哪条消息 timeout
- 实际选中的文本是什么
- console 报了什么错
- DOM 里到底有没有节点
- 接口返回的是 `null`、空数组，还是有结构但字段为空

一旦证据具体了，问题通常就会自动缩小。

### 第 5 步：区分“工具问题”和“产品问题”

这一步经常被忽略。

你看到的异常，可能来自：

- 扩展代码
- 构建产物
- 浏览器版本
- 调试协议
- 自动化脚本动作不准确

不要把这些全部混成“产品坏了”。

### 第 6 步：修一个问题后，回到真实链路重新走一遍

不要只看局部探针绿了。

比如消息不超时了，不代表页面就一定渲染对了。

所以每修完一层，都要重新走：

- 真实加载
- 真实划词
- 真实看结果

### 第 7 步：最后别忘了修“误导用户”的状态

哪怕底层逻辑对了，如果 UI 看起来像挂了，用户还是会判定它失败。

所以“明确的 empty state / error state / loading state”并不是装饰，而是可用性的一部分。
