# Vibe Coding 方法论探讨记录

> 日期：2026-02-17
> 背景：基于 ext-saladict MV2->MV3 迁移任务的多次尝试经历，探讨 AI Coding 的系统性问题与解决思路

---

## 1. 问题背景

### 1.1 任务经历

在 MV2->MV3 迁移任务中，先后尝试了多种工具和方法：

- **2025.4 Copilot**：Agent 能力太弱，经常超时和失败
- **2025.4 Cline + Gemini 2.5 Pro**：使用 memory-bank 解决跨会话问题，消耗 ~150 刀。Cline 声称完成但实际扩展加载报错。人工反馈循环（截图-修复-再测试）价值极低
- **2025.11 Antigravity + Gemini 3**：内置 Chrome DevTools MCP，减少了人工反馈环节。因网络和 quota 限制未跑通
- **2025.11 CC (Claude Code)**：消耗 2 亿 token，Chrome DevTools MCP 配置有问题导致浏览器操作能力受限。尝试了多 Agent 模式（plan + coding agent + TSE agent），表现一般
- **2026.2 CC + Claude 4.6**：当前尝试

### 1.2 每次尝试的收获

- Cline：尝试通过 memory-bank 解决跨会话上下文问题
- CC：尝试通过 sub-agent 做专家分工 + plan.md 记录进度
- 整体认知：
  - AI Coding 在逐渐变强
  - 上下文管理是核心问题，需要系统化工程，不是单靠 Prompt Engineering
  - 长任务如何收敛是关键问题
  - 工具的 browser-use 能力成熟度差异大

## 2. 核心讨论

### 2.1 软件工程的本质

软件工程本质上解决的问题可以用 5 个概念描述：

- **State**：当前系统真实状态（代码、测试、运行行为）
- **Intent**：目标状态（需求与成功判据）
- **Delta**：状态差距（待解决问题）
- **Evidence**：变化证据（证明 delta 在收敛）
- **Policy**：允许怎样改变系统（边界、风险、回滚）

这 5 个概念不是新发明，传统软件工程一直在做，只是分散在需求文档、设计评审、测试、发布流程里。

### 2.2 AI 对软件工程范式的影响

**核心洞察**：AI 降低了实现成本和试错成本，所以软件工程会从"前期一次性求确定"转向"后期持续求收敛"。

传统软件工程的局限性是写代码的成本和复杂度较高，需要在前期尽可能明确细节和需求。AI 降低了这个成本后，范式会发生变化：

- 以前优化"少改"，现在优化"快改 + 不炸"
- 兜底责任从"主要靠人执行"变成"人设计机制，机器按机制执行"
- AI 时代不是少做软件工程，而是要把软件工程做得更明确、更可检查

**与敏捷的关系**：敏捷已经在解决"不确定需求下的迭代交付"。AI 时代在敏捷基础上新增的问题是：代码产出太快，错误也扩散得太快。不是推翻敏捷，而是补充"如何防失控"。

### 2.3 Vibe Coding 的核心问题

**一句话定义**：快速验证代码和预期是否一致，为什么不一致，差在哪里。

这是所有编码任务的核心，不论 vibe coding 还是传统 coding。传统开发者能做到，是因为脑子里有"预期"，眼睛能看到"现实"，经验能定位"差在哪"。

Vibe Coding 下这三步都断了：

- **预期断了**：知道最终效果（扩展能用），但不知道中间状态的预期应该是什么
- **现实断了**：能看到最终现象（报错），但看不到中间状态的现实
- **差距定位断了**：既不清楚预期细节，也不清楚现实细节，无法定位 gap

### 2.4 循环困境

- 缺少可观测性 -> 任务不收敛
- 建立可观测性需要 domain knowledge -> 没有
- 希望 AI 帮建立可观测性 -> 没法验证 AI 建的对不对
- 没法验证 -> 因为缺少可观测性

过去每次尝试本质上都是试图从不同角度打破这个循环，但每次都卡回来了。

### 2.5 方法论类工具的局限

过去尝试的方法，都没有直接攻击"可观测性"这个真正瓶颈：

- memory-bank：解决的是跨会话记忆，不是可观测性
- sub-agent：解决的是分工，不是可观测性
- plan.md：解决的是计划跟踪，不是可观测性

## 3. 解决方向

### 3.1 核心命题

能不能让 AI 不只是写代码，而是让 AI 帮建立"预期-现实-差距"的可观测性本身？

传统做法：人建可观测性（人写测试、人定义预期、人判断差距），AI 只负责实现。

新思路：让 AI 用它的 domain knowledge 生成可执行的验证体系，人只看验证结果。

### 3.2 闭环设计（基于 ReAct）

```
Reason: 这个模块应该做什么？（AI 用 domain knowledge 推理）
Act:    写出验证这个预期的测试/探针
Observe: 跑测试，看结果
Reason: 通过了吗？没通过差在哪？
Act:    改代码或改测试
Observe: 再跑
...直到收敛
```

与传统 ReAct 的区别：传统 ReAct 里人在 Reason 环节深度参与；新版本里人只在 Observe 环节看数字。

### 3.3 与传统 SDD 的本质区别

- 传统 SDD：人定义预期，AI 实现
- 新思路：AI 定义预期，AI 实现，人只判断收敛性

### 3.4 关键风险

谁来验证 AI 定义的"预期"本身是对的？AI 可能写了一个测试，测试通过了，但测试本身就是错的。

但这个风险比原问题小得多：
- 验证"一个测试是否合理"比验证"一段实现是否正确"简单得多
- 测试的意图更容易被自然语言描述
- 不懂实现细节，但能判断"这个测试的目的对不对"
- 可以用另一个 AI 专门审查测试质量

### 3.5 Peer Review 机制

用 AI 审 AI 来部分补偿 domain knowledge 缺失：
- 实现者和审查者不能是同一个会话
- 审查者用对抗性指令（"找出问题"而不是"这个对不对"）
- 最好用不同模型，降低系统性偏见

局限：两个 AI 训练数据高度重叠，可能共享同一类盲区。能提高可靠性，但不能保证可靠性。

## 4. 当前项目真实状态（2026-02-17）

作为讨论的具体参照：

- `wxt build`：通过，4.56 MB，51.4s
- `npm test`：215 个测试，174 通过，27 失败，13 跳过
- 27 个 fail 大概率全部是迁移前预存在问题（merriamwebster 缺测试数据文件、webdav 同步服务、wikipedia 网络超时），与 MV3 迁移无关

- 任务难度判断：不是"复杂"，而是"最后一公里验证难"
